# annotation

Annotation Drawings are dashboard/listing-scoped Drawing resources rendered through the shared annotation overlay layer. Event-backed overlays retain their existing record contract.

## Invariants

- Market identity is `market: ProviderListing` from OpenChart; provider + symbol
  distinguish listings. Never require or fabricate V1 numeric listing IDs.

- Annotation Drawings belong to a dashboard and provider/listing through the Drawing Resource envelope. Their title, body, sources, sentiment and time are self-contained; they require no Event record. Chart.State.objects is their only chart collection. Event-backed overlays additionally reference their underlying event.
- For event-backed overlays, materialization provenance is all-or-none: `spanId`, `materializedByAgentRunId`, and `materializationKey` are either all present or all absent. The annotation row's unique run/key pair is the idempotency owner.
- Drawing annotations use `time` (numeric core seconds) and `anchors: []`; target price and automatic label geometry are render-owned; optional `labelAnchor` stores the user-dragged centroid. Event-backed overlays use `anchor.start`/`anchor.end` in epoch seconds as the semantic temporal anchor. Optional `targetAnchor` is the chart-space leader target and optional `labelAnchor` is the chart-space manual pill placement point, using the same time/price anchor primitive as drawings; do not persist renderer-derived lanes, pixel rectangles, bar indexes, or solver scores.
- `style` is user-authored visual intent for the annotation label, leader, and handles. It reuses drawing style fields so shared toolbar controls can edit annotations for event-backed overlays. Annotation Drawings use the normal Drawing Resource collection.
- Annotation style defaults must resolve to the same pill colors for persisted records and transient drafts; `Schema.decodeUnknownSync(ChartAnnotation.Style)({})` is the canonical default style for both paint paths and must point at the theme-owned `--chart-annotation-*` tokens rather than hardcoded renderer colors.
- Event instants never change with resolution. Within the loaded timeline, the
  leader uses the last bar start at or before the instant, never the nearest
  future bar. Times outside loaded endpoints stay unresolved; core does not
  infer missing trading periods or extend the last bar's coverage.

- Agent-backed annotations are runtime-marked by `agentAnnotationIds`; source badges and expanded-card content are decoration/projections, not the sole source of agent semantics. Agent-backed rendering ignores persisted `style`: pill/card fill and text come from theme-owned AI annotation fill/text tokens, while leader, border, and target anchor accent come from annotation sentiment via theme-owned AI annotation accent tokens resolved by `resolveAgentAnnotationStyle`, not candle `--up`/`--down` colors.
- `appearance.ts` owns annotation overlay geometry: pill height/radius, text padding, source-badge slot, target-dot radius, and leader gap. Layout and paint must read this shared appearance instead of duplicating constants.
- Source logos/badges are runtime decoration. Drawing badges derive from persisted source links; event-backed badges derive from event sources. Pass them into layout/render via source-badge maps keyed by annotation id or event id; do not denormalize event evidence onto annotation records.
- Canvas publisher logos must load only from same-origin/proxied/CORS-safe image URLs and fall back to deterministic initials/colors on load failure; DOM expanded cards can render remote logos as ordinary images.
- Loaded canvas source logos preserve their transparent pixels over the annotation surface. The deterministic hash color is only the missing/loading/failed-logo fallback; a source must set `color` explicitly when its logo requires a persistent plate.
- Expanded Drawing cards derive title/body from the Drawing. Full-body disclosure is transient interaction state; core publishes body truncation and the same expanded rectangle consumed by DOM chrome. Event-backed cards obtain title/body/questions from runtime event metadata. Pass them into layout/render as lightweight sizing/content metadata so canvas leader geometry and DOM chrome share one rectangle without DOM measurement.
- For event-backed overlays, user feedback on whether an explanation is useful is persisted on the annotation record, not event metadata or local UI state. Feedback is nullable until the user responds and must travel through the same annotation update contract as other annotation fields.
- Runtime source badges mark agent-sourced annotations for interaction purposes. Their first/target anchor is event-owned; annotation leader targets must resolve to one of two wick-side points at the same event time: above the upper wick or below the lower wick. A moved `labelAnchor` chooses between those two targets from the pill centroid relative to the candle midpoint, and an explicit `targetAnchor` snaps to the closest allowed wick-side target. For event-backed overlays, users may move the label anchor/pill placement, but visible target handles must never sit on top of the candle body or wick.
- Transient draft annotations must be projected through `createDraftAnnotationRecord` before layout/paint; do not hand-build draft records in paint or event code.
- Runtime layout owns candle resolution, leader target choice, label rectangles, layering, and hover expansion. Paint and hit-testing must consume the same layout geometry. `ChartAnnotationLayoutState` is runtime-only: it may remember compact slot offsets across pan/zoom renders, but it must never be serialized or promoted into the annotation record.
- Annotation layout is not a crosshair primitive. Canvas paint may cache layout/raster results across crosshair-only frames, and hit-testing should consume the last painted placements instead of solving the raster placement problem on every pointer move.
- Pointer hit-testing should consume the renderer's last painted z-ordered hit
  placements when available. Do not sort or expand the full annotation placement
  set on every crosshair move unless an immediate interaction override requires
  a frame-local expanded projection.
- The layout solver first produces stable compact placements for all annotations; expanded agent cards are derived from the compact placement after solving. Hover state may expand an agent card, but active selection alone must keep it compact unless hover/drag ownership is present. Hover/active state must not reorder targets or re-run neighboring labels through a different placement problem.
- Runtime placement should prefer a still-valid previous compact slot or manual `labelAnchor` before searching new candidates. Cached runtime slots preserve the previous anchor-to-pill-centroid vector across horizontal panning, then clamp only when the resulting pill would leave the viewport; they must not make every non-edge annotation viewport-sticky. Cached runtime slots must invalidate when the chart area, pill size, or horizontal scale changes so zoom/resolution changes can re-solve adaptively. Cached runtime slots must remain inside the leader cap, but chart-ink overlap alone must not invalidate or re-score them during pan. Manual `labelAnchor` positions are user-authored drag state and must be honored even when they temporarily exceed the automatic leader cap. Valid sticky placements must not generate or score the full local candidate ring set; drag and pan/zoom paths depend on that fast path.
- Pure viewport translation may reuse the last painted compact placements by preserving each annotation's anchor-to-pill-centroid vector and refreshing only candle/leader anchor geometry. That translation path must not rebuild chart occupancy, run candidate elimination, or write clamped frame rectangles back into `ChartAnnotationLayoutState`; viewport push/clamp is ephemeral and only for labels whose translated rect would clip. If visible annotations, pill sizes, hover expansion, or scale shape change, fall back to the full solver.
- Automatic compact placement is a single bounded greedy pass over anchor-local candidate rings. Candidate rings are generated around the resolved candle/target anchor, then eliminated/scored for chart-ink overlap, label overlap, balance, and leader crossings. Within each elimination class, vertically aligned above/below candidates are preferred across all rings before side/diagonal candidates so labels stay directly connected to their event when vertical space exists. Leader crossing minimization is part of elimination, not only a late score tiebreaker. Do not reintroduce broad global lane candidates that can make a label jump far away from its anchor before local candidates are exhausted.
- Automatic placement candidates are compound raster masks, not only label rectangles. The placement occupancy model must account for pill footprint and leader footprint together, provide fast clean-conflict checks, and expose overlap counts for dense fallback. The target dot may be committed as annotation occupancy so later annotations avoid it, but it must not make the annotation conflict with the candle it intentionally anchors to.
- Local occupancy-map debug views must be projections of the same raster bitmaps used by placement. Do not rebuild a separate chart-ink or annotation mask path for diagnostics; bugs in the debug view should indicate bugs in the real placement bitmap or its projection.
- Hover ownership wins over selected/active ownership for expanded-card layout. Once an annotation is hovered, hit-testing must retain that annotation while the pointer remains inside its compact/expanded hover envelope, even if neighboring layered annotations overlap.
- Target/first-anchor handles are draggable hit targets, not hover owners. Hovering a target dot must not expand an agent annotation card; only the annotation pill/card body owns expansion.
- Visible annotation pill geometry and hit geometry must agree. Do not draw a full compact pill while only exposing a small strip to hit-testing; z/layer ordering should resolve conflicts among overlapping visible pills.
- Agent-backed expanded annotation cards are the expanded state of the same runtime placement, not separate popovers. Their card rectangle is still `AnnotationPlacement.pill`, and drag/hit behavior must continue to operate on that rectangle. Expanded placements may carry `compactPill` as runtime transition geometry for DOM chrome; it is a projection of the compact placement and must not become persisted annotation state.
- Agent annotation hover and click states are intentionally distinct: hover may widen the compact pill and expose an expand affordance, while `expandedAnnotation` owns the card identity and preview/full-body disclosure together; closing clears both. Hover widening must be available from the annotation identity/title itself; the richer expanded-card payload is required only for click-to-card. Compact and hover pills are canvas-owned; DOM chrome must not duplicate them. The full card must collapse when hover ownership leaves the annotation/card body.
- Clicking any visible part of an agent pill body, including its source badges, expands the card when expanded content exists. The same body remains draggable: only a pointer sequence that ends without movement is a click-to-expand.
- Overflowing agent pill labels keep their compact ellipsis at rest and use a canvas-owned, continuous marquee while hovered. The marquee is paint-only, must not alter layout or hit geometry, and must stop entirely under reduced-motion preferences.
- Hover widening must expose its final layout geometry atomically. Do not animate `AnnotationPlacement.pill`, `actionButton`, or hit rectangles inside the core layout solver; visual easing belongs in canvas paint projections for pills and DOM chrome projections for expanded cards so paint, hit-testing, and controls never disagree about the pixel rectangle.
- `labelAnchor` is the semantic second anchor and always maps to the annotation rectangle centroid. Manual creation drops the pill/card centroid at the second pointer; dragging the pill body or label handle hit area updates this centroid anchor. Do not paint a visible centroid knob through the annotation body; expanded cards remain centered on the same centroid so dragging stays continuous.
- Leader lines are visual geometry derived from target anchor to annotation centroid, then clipped to the current pill/card boundary. They must shorten and re-angle when a compact pill expands into a card, without introducing a separate persisted or interactive second anchor. Non-collapsed placement must not emit leaders longer than the layout-owned maximum; placement scoring should strongly prefer labels that avoid chart ink such as candlestick bodies and wicks, while still tolerating overlap when density leaves no clean slot.
- Dense automatic placement may layer or tolerate overlap only after anchor-local candidates have been eliminated. Empty chart regions are valid only when they are reachable within the leader-length cap; do not prefer a remote clean region over a nearby imperfect candidate.
- Leader segments are not hover/select geometry. Annotation hover and drag ownership begins at the annotation rectangle or visible handles only, so nearby or overlapping leader lines cannot steal expansion state.
